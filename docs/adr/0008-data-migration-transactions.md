# Data migration preserves immutable history and restores verified local capabilities

History remains immutable Pack union with Source-owned branches (ADR 0006/0007). Migration has separate durable decisions for history, configuration, payload installation, local replicas and Workspace continuation. A history commit or valid local-state document alone does not establish that a historical version is restorable.

## Decisions

- The normal UI exports v3 `.frhistory` bundles with explicit project selection, optional portable configuration and optional payloads. Configuration-only export remains JSON. Readers retain v1 single-project and v2 multi-project history compatibility; advanced metadata-only export remains v2. Reports distinguish committed history, configuration activation, password preparation, verified replicas, continuation and per-version readiness.
- v3 preserves ConfigId, SourceId and original Pack bytes, and carries archive-relative paths, sizes and SHA-256 hashes plus candidate Workspace continuation. Passwords, DPAPI ciphertext and device cloud credentials are excluded. The default references external archives; a complete bundle includes every declared version's exact representation dependency closure and required Artifact ledger closure. Missing closure members fail complete export.
- Payloads stream through the package. Metadata is limited to 64 MiB per item and 512 MiB in total; entries are canonical, unique and bounded. Import validates entry declarations, hashes, target paths, link boundaries, conflicts, cancellation and available space. Installation stages all new files before a durable forward-recovery decision; an existing conflicting file is preserved.
- Preserve ConfigId, SourceId and Pack bytes. An orphan waits for the original configuration; project names and path hints are not identities. Runtime cache presence does not determine association.
- New multi-Pack unions are staged in `imports/<id>/`. Before the durable union decision, failure/cancellation leaves existing facts unchanged. After it, retained staged bytes allow idempotent forward recovery. Incomplete unions block repository reads/mutations and recover before graph validation and index rebuilding.
- A normal single Commit Pack retains its existing final-file commit decision and local-state journal. A union intent must not cause capture cleanup to delete payloads for history that can later commit.
- Explicit transfer marks intentionally missing local state as initialization required. Unmarked missing state, corruption, inaccessible files and incomplete prior transactions retain recovery semantics.
- Controlled setup creates Unknown source baselines and an empty local replica catalog only where missing. Valid state survives import. A separate replica-recovery service finds candidates only in confirmed backup roots, retains valid entries, checks known hashes and tests actual archives. Legacy hashless candidates require explicit confirmation after archive validation; ambiguous candidates require individual selection. Local-state decisions are revision checked and journaled.
- Encrypted migration and restore share old-password preparation. A submitted password must verify actual encrypted archives and their dependencies before atomic DPAPI storage and readback. An unreadable stored entry is not considered ready, and save failure is surfaced. Wrong passwords and cancellation preserve valid credentials.
- Continuation hints are untrusted candidates. A unique valid branch may be preselected; multiple branches require selection, and competing tips require existing reconciliation. Continuation validates Source identity, branch tip, checkpoint, effective boundary and actual content. Matching current content establishes Exact and rebuilds the disposable capture cache. Different content remains untouched, restores the confirmed branch/checkpoint pointers, and stays Unknown with `RequiresFullCapture`.
- Workspace v4 reads v3 and makes `RequiresFullCapture` durable. The flag excludes cached baselines, automatic cache repair, unchanged reuse and incremental captures. The next successful capture must be self-contained and cover the full effective Source; its historical parent is the confirmed checkpoint version, and it commits on the original BranchId. The same local-state transaction clears the flag only after successful publication. Failure, cancellation and restart preserve it. A Source without history creates its first default branch; existing accidentally created branches remain available.
- Configuration import prepares an immutable candidate. The running configuration and its save queue remain active. At restart, the old process drains its writer; the new process creates a safety copy and activates before windows, plugins, Runtime warmup or automation. Interrupted/uncommitted activation rolls back. Applied imports require per-project setup confirmation tied to that particular import.
- Unified imports merge selected projects by identity and retain unselected projects and their setup evidence. Existing installations retain global preferences; empty installations use portable package preferences. Setup registry v3 records the import token and prior configuration evidence per project. Explicit configuration import awaiting history stays paused and displays that state; an unrelated bound project with a missing descriptor retains its recovery error.
- Configuration preserves automation/cloud switches. Versioned device-local permissions pause backup and cloud uploads independently per project; one batch confirmation releases selected ready capabilities without replaying startup backups or uploading existing archives. Config activation and its active permission registry roll back together.
- Local restore retains valid workspace/replica state when target identities, source paths and semantics match the pre-import configuration. Cross-device initialization keeps Unknown state. A mode selection is not evidence; damaged state still requires recovery.
- A Host migration state document retains the selected project, package hash, cached bundle, configuration activation token and completed configuration signature. Committed Pack unions survive later configuration or local-setup failure. Prepared payload installation and local-state journals recover forward; incomplete project stages can be retried independently. A path change invalidates prior preparation rather than admitting backup with stale evidence.
- Batch inspection is read-only and verifies metadata, local state and connection evidence. Confirmation rechecks under the configuration-operation lease. Per-project failures/cancellation retain already completed decisions. Target cloud bindings are reused only for matching projects/connections; cloud readiness cannot block local backup.
- v1 transaction/confirmation records remain readable. Preferences erased by earlier builds are never guessed; the user can reread switches from an original export with matching project/source identities, without replacing paths, rules or credentials. History-only local initialization also retains a separate confirmation requirement.
- Local files and cloud snapshots use the same package validation and import services. Cloud snapshots are independent immutable exports under `_folderrewind/migration-exports/`. Upload publishes its manifest only after downloading and verifying the uploaded payload's length and SHA-256. Listing exposes published manifests; download verifies the selected version before atomic publication and removes temporary files on failure or cancellation. This does not grant project cloud-upload permission.

## Consequences

An import can succeed in publishing history while still requiring configuration activation, password entry, archive checks, branch selection or transaction recovery. Reports retain committed facts and state the actual restore readiness of each version. Ready projects can resume local backup while other projects or cloud bindings remain pending.

Regression uses real archives (including encrypted Full plus Smart dependencies), isolated new-install imports, real rclone local-backend transfers, and WinApp CLI interface acceptance. An original encrypted project still requires its original password; a real remote cloud acceptance requires a prepared connection. Native repository formats and plugin public contracts remain unchanged.
